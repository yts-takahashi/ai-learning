## 技術選定の記録

### なぜ Next.js 15 App Router か

Next.js のApp Router（バージョン13以降の新しいルーティング方式）は、ページをサーバーサイドで描画する「Server Components」をデフォルトにした。eラーニングのレッスンページはインタラクション不要な静的コンテンツが主体であり、Server Components との相性が良い。クイズや進捗管理など、ブラウザ側の動作が必要な部分だけ `"use client"` を付けて切り分けることで、不必要なJavaScriptをクライアントに送らずに済む。

却下した選択肢としてはPages Router（旧方式）がある。App Routerの方がServer Actionsによるデータ取得・ローディング状態の管理・並列データフェッチが直感的に書けるため、フェーズ2以降の機能拡張を見据えて採用した。

### なぜ Tailwind CSS v4 か

Tailwind CSS v4は設定ファイル（`tailwind.config.js`）が不要になり、`globals.css` に `@import "tailwindcss"` を一行書くだけで動く。設定ファイルが減ることでAIが誤って設定を壊すリスクが下がる。これは自律開発との相性が特に良い。

v3との後方互換性を捨てて大きく変わったバージョンだが、このプロジェクトは初期から始めるため移行コストがかからない。Turbopack（Next.jsの高速バンドラー）との組み合わせで、開発サーバーの起動が劇的に速い。

却下した選択肢：CSS Modules（コンポーネントごとにファイルが増えてAIが管理しにくい）、styled-components（Runtime CSS-in-JSはSSRと相性が悪い）。

### なぜ Markdown ファイルでコンテンツ管理か

121本のレッスンコンテンツをデータベースで管理する選択肢もあったが、Markdownファイルを選んだ理由は3つある。

1. **AIが書きやすい**: Claude CodeはMarkdownを自在に生成できる。構造化されたJSONやDBスキーマよりも、自然言語に近いMarkdownの方がコンテンツ品質が高くなる。
2. **gitで管理できる**: コンテンツの変更履歴がコードと同じgitリポジトリで追える。フロントマター（各ファイルの冒頭にあるメタデータ）でタイトル・チャプター・難易度・所要時間を管理する。
3. **静的生成と相性が良い**: ビルド時にMarkdownをHTMLに変換する静的サイト生成戦略を取れば、表示速度が速く、サーバーコストもかからない。

パーサーには `gray-matter`（フロントマターの解析）と `next-mdx-remote`（MarkdownをReactコンポーネントとしてレンダリング）を採用予定だ。

## ハーネスエンジニアリングの実践

このプロジェクト自体がChapter 10「ハーネスエンジニアリング・自律開発」の題材になっている。実際にどう実践しているかを記録しておく。

### CLAUDE.md による文脈提供

CLAUDE.md はClaude Codeが起動するたびに自動で読み込まれる設定ファイルだ。ここにプロジェクトの技術スタック・コマンド・ディレクトリ構成・基本規約を書く。

**重要な教訓**: 最初は詳細すぎるCLAUDE.mdを作ってしまった。コンポーネント命名規則・インポート順序・禁止事項まで全部書いたが、「常時読み込まれる = コンテキストウィンドウを常に消費する」という事実に気づいてスリム化した。詳細な規約はそれぞれのスキルに分離した。最終的に、CLAUDE.mdには「いつでも必要な最小限の情報」だけを残すというポリシーに落ち着いた。

### スキルによる役割分担

スキル（`.claude/skills/` に置くMarkdownファイル）は、特定の作業を依頼したときだけ読み込まれる。Progressive Disclosure（段階的開示）の原理で、通常時はメタデータのみ、発動時に詳細な手順書が展開される。

このプロジェクトで定義したスキル：

| スキル | 役割 |
|---|---|
| `ship` | PRDの全タスクを設計〜実装〜コミットまで自律実行するオーケストレーター |
| `content` | 121本の教材レッスンをMarkdownで並列作成するスペシャリスト |
| `chronicle` | 開発プロセスを記録し開発ジャーナルを書く記録担当 |
| `launch` | ship・content・chronicle を3並列で起動する最上位オーケストレーター |
| `develop` | 1機能を設計〜コミットまで完結させるオーケストレーター |
| `design` | 機能の設計・仕様書作成 |
| `page` | Next.jsページコンポーネントの作成 |
| `component` | Reactコンポーネントの作成 |
| `commit` | Conventional Commits形式で日本語コミットメッセージを生成（グローバル配置） |

### サブエージェントによる並列実行

`launch` スキルは3つのサブエージェントを並列で起動する：

- **エージェントA（ship）**: アプリの実装を担当
- **エージェントB（content）**: 121レッスンの教材を作成
- **エージェントC（chronicle）**: 開発ジャーナルを記録

なぜ並列にするか。アプリ実装とコンテンツ作成は互いに独立している。直列で実行すれば片方が終わるまで待たなければならないが、並列なら総所要時間を大幅に短縮できる。自律開発において、独立したトラックは最初から並列で設計することが重要だ。

## アーキテクチャの意思決定

### 型定義を先に作った理由

`src/lib/types.ts` に `Lesson` / `Chapter` / `QuizQuestion` / `Progress` のインターフェースを定義した。実装の前に型を定義する理由は、AIが複数のファイルにまたがるコードを書く際に型が「共通言語」として機能するからだ。型定義があれば、ページコンポーネント・コンテンツローダー・クイズ機能がバラバラに実装されても、型エラーという形で不整合が検出される。

### PostToolUse フックによる品質ゲート

`.claude/settings.json` に設定した PostToolUse フックは、Claudeがファイルを編集するたびに自動で `npm run lint` と `npx tsc --noEmit` を実行する。フックはHooksと呼ばれるClaude Codeの仕組みで、ツール呼び出しの前後に任意のコマンドを差し込める。

これが自律開発において不可欠な理由は、「AIが間違えたとき、自分で気づいて直せる」からだ。人間が目視でレビューしなくても、型エラー・Lintエラーはフックが即座に検知し、Claudeに通知する。長時間の無人実行を安全に続けるための安全網だ。

### `content/` ディレクトリは未作成

現時点で `content/lessons/` は存在しない。教材コンテンツはフェーズ3で `content` エージェントが作成する。先にディレクトリだけ作っておく手もあるが、空ディレクトリはgitに残らないため、最初のレッスンファイルが作成された時点で自然に生まれる設計にした。

## 学びと気づき

### 「作る前の設計」に時間をかける価値

自律開発では、環境設計に投資した時間が後で何倍にもなって返ってくる。今日一日でCLAUDE.md・フック・スキルを整えたことで、明日以降はlaunchコマンド一言で3トラック並列の開発が自動で走る。

### PRD駆動開発の重要性

「何が完成した状態か」を定義しないまま自律実行を開始すると、AIは必ず途中で止まるか、的外れな実装をする。PRDに全タスクをチェックリスト形式で書いたのはそのためだ。`ship` スキルはPRDのチェックボックスを上から順に実行し、完了したものを `[x]` に変えていく。PRDが進捗管理ツールも兼ねる。

### このeラーニングが「題材として適切」な理由

教育コンテンツの制作は、実装とコンテンツ作成という2つの独立したトラックを持つ。これが並列実行の有効性を示すのに最適な題材だ。さらに、Chapter 10でこのプロジェクト自体を教材にするという入れ子構造（メタ学習）は、ハーネスエンジニアリングを概念としてではなく実体験として学ぶ唯一の方法だ。読者は「ハーネスエンジニアリングとはこういうものだ」という説明を読むだけでなく、「このeラーニングはそうやって作られた」という事実と一緒に受け取る。

### 10チャプター・121レッスンという構成の意図

単にトピックを羅列したのではない。Chapter 1〜3は「プロンプトを書く → APIを叩く → RAGとエージェントを作る」という実践の積み上げ。Chapter 4〜6は「ビジネス応用 → モデルを自分で育てる → セキュリティを守る」という応用層。Chapter 7〜9は「ツール連携 → 品質保証 → スケールする設計」というプロエンジニアの領域。そしてChapter 10だけが「開発プロセスそのもの」を扱う異質な章であり、このeラーニングの開発を題材にした締めくくりになっている。

## 自律開発の起動手順

### 初回セットアップ
```bash
brew install tmux   # tmuxのインストール（初回のみ）
```

### 毎回の起動手順（寝る前など）
```bash
# 1. tmuxセッションを作成
tmux new -s ai-learning

# 2. プロジェクトへ移動
cd ~/git/ai-learning

# 3. Claude起動
claude

# 4. 指示を出す
#    「launchして」

# 5. 動き出したのを確認してデタッチ（バックグラウンドに回す）
#    Ctrl+B → D
```

### 進捗確認・再開
```bash
tmux attach -t ai-learning   # セッションに戻る
```

> **tmux とは**: ターミナルを閉じてもセッションを維持できるターミナルマルチプレクサ。これがないと、PCのスリープ中にClaude Codeが止まってしまう。自律開発のインフラとして不可欠なツールだ。

### 実装ハイライト

#### launch スキルによる並列コンテンツ作成

**何を作ったか**

Chapter 3「RAG・エージェント」（13レッスン）・Chapter 4「ビジネス活用事例」（10レッスン）・Chapter 5「ファインチューニング」（11レッスン）の合計31レッスンをAgent1が担当し、Chapter 6「セキュリティ・レッドチーム」（11レッスン）・Chapter 7「MCP・ツール連携」（10レッスン）・Chapter 8「プロンプトの評価・テスト」（11レッスン）・Chapter 9「AI開発のアーキテクチャ設計」（11レッスン）・Chapter 10「ハーネスエンジニアリング・自律開発」（12レッスン）の合計55レッスンをAgent2が担当した。

各レッスンはフロントマター（タイトル・チャプター番号・難易度・所要時間）を持つMarkdownファイルとして `content/lessons/chapter-XX/` 配下に生成される。記事本文・ハンズオン・クイズの3セクション構成をすべてのレッスンに統一することが品質基準だ。

**設計の意図**

今回の分割には明確な意図がある。Chapter 3〜5 は「RAG・エージェント → ビジネス活用 → ファインチューニング」という技術深化のトラックであり、概念の連続性が高い。一方、Chapter 6〜10 は「セキュリティ → MCP → 評価 → アーキテクチャ → ハーネスエンジニアリング」という横断的な応用トラックだ。この2つを別エージェントに担当させることで、前半エージェントが技術深化系のコンテキストを維持したまま執筆でき、後半エージェントは応用・実践系のトーンに集中できる。

単純に「レッスン数が多いから2分割」するのではなく、**コンテキストの連続性を保ちやすい単位で分割する**ことがコンテンツ品質を守る。これがエージェントへのタスク分割設計の核心だ。

**技術的なポイント**

並列実行の最大のリスクは、2つのエージェントが同じファイルパスに書き込もうとする競合だ。今回はChapter番号でディレクトリを分けているため、ファイルシステムレベルの競合は発生しない。Agent1は `chapter-03/` 〜 `chapter-05/`、Agent2は `chapter-06/` 〜 `chapter-10/` とI/O領域が完全に分離されている。

この「作業空間の非重複設計」は並列エージェントを安全に走らせる最もシンプルかつ確実な方法だ。ロックやトランザクション制御を考える前に、まず作業領域を物理的に分けられないか検討するべきだ。

### 意思決定メモ

**なぜChapter 10まで一気に作るか**

Chapter 10「ハーネスエンジニアリング・自律開発」は、このeラーニング全体の締めくくりであり、「このeラーニング自体がどう作られたか」を題材にする章だ。コンテンツが完成してから執筆するのではなく、コンテンツを作りながら同時にChapter 10の素材を蓄積していく。つまり今日の開発記録は、そのままChapter 10 レッスン12「ハーネスエンジニアリングの実践例」の一次資料になる。

開発プロセスと教材コンテンツが互いに相互参照する構造—これがこのプロジェクトの最も面白い設計だ。

**コンテンツの品質基準の維持**

121レッスンを自動生成する際のリスクは「均質な薄いコンテンツ」になることだ。これを防ぐため、`content` スキルには各レッスンのフォーマット（記事・ハンズオン・クイズの3セクション）・文字数の目安・具体的なコードサンプルの含め方を詳細に定義している。スキルがエージェントへの「品質基準書」として機能することで、量産しながらも基準を落とさない仕組みを作る。

### ハーネスエンジニアリングの学び

**並列実行のメリットは時間短縮だけではない**

86レッスンを1エージェントで直列作成した場合と2エージェントで並列作成した場合の差は、単純な時間短縮にとどまらない。エージェントのコンテキストウィンドウには有限の容量がある。1エージェントに86レッスン全部を任せると、後半レッスンを書く頃には前半の細かい文体・構成パターンの記憶が薄れ、スタイルのドリフト（文体・品質の揺れ）が発生しやすくなる。2エージェントに分割することでコンテキストを分散させ、各エージェントが担当範囲の前後関係を鮮明に保ちながら書けるようにする。

**スキルは「仕様書」であり「品質ゲート」でもある**

`content` スキルをエージェントに渡すとき、そのMarkdownファイルは単なる作業手順書ではない。「どういうレッスンを作れば合格か」という合格基準が埋め込まれた検査仕様書でもある。エージェントはスキルを読みながら自分の出力を自己チェックする。人間がレビューしなくても、スキルに書かれた基準からの逸脱をエージェント自身が検知できる。これが「ハーネス」の本質—実行環境に品質基準を織り込む設計だ。

**コンテンツ作成完了後の次フェーズ**

86レッスンが完成すれば、残りはChapter 2の未完分1レッスンを含めて全121レッスンが揃う。その後はPRDのフェーズ3チェックボックスを `[x]` にマークし、アプリとコンテンツが統合された状態でブラウザ確認を行う。開発ジャーナルの最終エントリはそのタイミングで記録する予定だ。
