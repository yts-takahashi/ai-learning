このプロジェクトは、生成AIを体系的に学びたいエンジニア向けのeラーニングWebアプリケーションだ。プロンプトエンジニアリングに始まり、API活用・RAG・エージェント・ファインチューニング・セキュリティ・MCP・評価・アーキテクチャ設計、そして「ハーネスエンジニアリング（AIの力を最大限に引き出すための環境設計）」まで、全10チャプター・121レッスンを網羅する。

## 技術選定の記録

### なぜ Next.js 15 App Router か

Next.js のApp Router（バージョン13以降の新しいルーティング方式）は、ページをサーバーサイドで描画する「Server Components」をデフォルトにした。eラーニングのレッスンページはインタラクション不要な静的コンテンツが主体であり、Server Components との相性が良い。クイズや進捗管理など、ブラウザ側の動作が必要な部分だけ `"use client"` を付けて切り分けることで、不必要なJavaScriptをクライアントに送らずに済む。

却下した選択肢としてはPages Router（旧方式）がある。App Routerの方がServer Actionsによるデータ取得・ローディング状態の管理・並列データフェッチが直感的に書けるため、フェーズ2以降の機能拡張を見据えて採用した。

### なぜ Tailwind CSS v4 か

Tailwind CSS v4は設定ファイル（`tailwind.config.js`）が不要になり、`globals.css` に `@import "tailwindcss"` を一行書くだけで動く。設定ファイルが減ることでAIが誤って設定を壊すリスクが下がる。これは自律開発との相性が特に良い。

v3との後方互換性を捨てて大きく変わったバージョンだが、このプロジェクトは初期から始めるため移行コストがかからない。Turbopack（Next.jsの高速バンドラー）との組み合わせで、開発サーバーの起動が劇的に速い。

却下した選択肢：CSS Modules（コンポーネントごとにファイルが増えてAIが管理しにくい）、styled-components（Runtime CSS-in-JSはSSRと相性が悪い）。

### なぜ Markdown ファイルでコンテンツ管理か

121本のレッスンコンテンツをデータベースで管理する選択肢もあったが、Markdownファイルを選んだ理由は3つある。

1. **AIが書きやすい**: Claude CodeはMarkdownを自在に生成できる。構造化されたJSONやDBスキーマよりも、自然言語に近いMarkdownの方がコンテンツ品質が高くなる。
2. **gitで管理できる**: コンテンツの変更履歴がコードと同じgitリポジトリで追える。フロントマター（各ファイルの冒頭にあるメタデータ）でタイトル・チャプター・難易度・所要時間を管理する。
3. **静的生成と相性が良い**: ビルド時にMarkdownをHTMLに変換する静的サイト生成戦略を取れば、表示速度が速く、サーバーコストもかからない。

パーサーには `gray-matter`（フロントマターの解析）と `next-mdx-remote`（MarkdownをReactコンポーネントとしてレンダリング）を採用予定だ。

## ハーネスエンジニアリングの実践

このプロジェクト自体がChapter 10「ハーネスエンジニアリング・自律開発」の題材になっている。実際にどう実践しているかを記録しておく。

### CLAUDE.md による文脈提供

CLAUDE.md はClaude Codeが起動するたびに自動で読み込まれる設定ファイルだ。ここにプロジェクトの技術スタック・コマンド・ディレクトリ構成・基本規約を書く。

**重要な教訓**: 最初は詳細すぎるCLAUDE.mdを作ってしまった。コンポーネント命名規則・インポート順序・禁止事項まで全部書いたが、「常時読み込まれる = コンテキストウィンドウを常に消費する」という事実に気づいてスリム化した。詳細な規約はそれぞれのスキルに分離した。最終的に、CLAUDE.mdには「いつでも必要な最小限の情報」だけを残すというポリシーに落ち着いた。

### スキルによる役割分担

スキル（`.claude/skills/` に置くMarkdownファイル）は、特定の作業を依頼したときだけ読み込まれる。Progressive Disclosure（段階的開示）の原理で、通常時はメタデータのみ、発動時に詳細な手順書が展開される。

このプロジェクトで定義したスキル：

| スキル | 役割 |
|---|---|
| `ship` | PRDの全タスクを設計〜実装〜コミットまで自律実行するオーケストレーター |
| `content` | 121本の教材レッスンをMarkdownで並列作成するスペシャリスト |
| `chronicle` | 開発プロセスを記録し開発ジャーナルを書く記録担当 |
| `launch` | ship・content・chronicle を3並列で起動する最上位オーケストレーター |
| `develop` | 1機能を設計〜コミットまで完結させるオーケストレーター |
| `design` | 機能の設計・仕様書作成 |
| `page` | Next.jsページコンポーネントの作成 |
| `component` | Reactコンポーネントの作成 |
| `commit` | Conventional Commits形式で日本語コミットメッセージを生成（グローバル配置） |

### サブエージェントによる並列実行

`launch` スキルは3つのサブエージェントを並列で起動する：

- **エージェントA（ship）**: アプリの実装を担当
- **エージェントB（content）**: 121レッスンの教材を作成
- **エージェントC（chronicle）**: 開発ジャーナルを記録

なぜ並列にするか。アプリ実装とコンテンツ作成は互いに独立している。直列で実行すれば片方が終わるまで待たなければならないが、並列なら総所要時間を大幅に短縮できる。自律開発において、独立したトラックは最初から並列で設計することが重要だ。

## アーキテクチャの意思決定

### 型定義を先に作った理由

`src/lib/types.ts` に `Lesson` / `Chapter` / `QuizQuestion` / `Progress` のインターフェースを定義した。実装の前に型を定義する理由は、AIが複数のファイルにまたがるコードを書く際に型が「共通言語」として機能するからだ。型定義があれば、ページコンポーネント・コンテンツローダー・クイズ機能がバラバラに実装されても、型エラーという形で不整合が検出される。

### PostToolUse フックによる品質ゲート

`.claude/settings.json` に設定した PostToolUse フックは、Claudeがファイルを編集するたびに自動で `npm run lint` と `npx tsc --noEmit` を実行する。フックはHooksと呼ばれるClaude Codeの仕組みで、ツール呼び出しの前後に任意のコマンドを差し込める。

これが自律開発において不可欠な理由は、「AIが間違えたとき、自分で気づいて直せる」からだ。人間が目視でレビューしなくても、型エラー・Lintエラーはフックが即座に検知し、Claudeに通知する。長時間の無人実行を安全に続けるための安全網だ。

### `content/` ディレクトリは未作成

現時点で `content/lessons/` は存在しない。教材コンテンツはフェーズ3で `content` エージェントが作成する。先にディレクトリだけ作っておく手もあるが、空ディレクトリはgitに残らないため、最初のレッスンファイルが作成された時点で自然に生まれる設計にした。

## 学びと気づき

### 「作る前の設計」に時間をかける価値

自律開発では、環境設計に投資した時間が後で何倍にもなって返ってくる。今日一日でCLAUDE.md・フック・スキルを整えたことで、明日以降はlaunchコマンド一言で3トラック並列の開発が自動で走る。

### PRD駆動開発の重要性

「何が完成した状態か」を定義しないまま自律実行を開始すると、AIは必ず途中で止まるか、的外れな実装をする。PRDに全タスクをチェックリスト形式で書いたのはそのためだ。`ship` スキルはPRDのチェックボックスを上から順に実行し、完了したものを `[x]` に変えていく。PRDが進捗管理ツールも兼ねる。

### このeラーニングが「題材として適切」な理由

教育コンテンツの制作は、実装とコンテンツ作成という2つの独立したトラックを持つ。これが並列実行の有効性を示すのに最適な題材だ。さらに、Chapter 10でこのプロジェクト自体を教材にするという入れ子構造（メタ学習）は、ハーネスエンジニアリングを概念としてではなく実体験として学ぶ唯一の方法だ。読者は「ハーネスエンジニアリングとはこういうものだ」という説明を読むだけでなく、「このeラーニングはそうやって作られた」という事実と一緒に受け取る。

### 10チャプター・121レッスンという構成の意図

単にトピックを羅列したのではない。Chapter 1〜3は「プロンプトを書く → APIを叩く → RAGとエージェントを作る」という実践の積み上げ。Chapter 4〜6は「ビジネス応用 → モデルを自分で育てる → セキュリティを守る」という応用層。Chapter 7〜9は「ツール連携 → 品質保証 → スケールする設計」というプロエンジニアの領域。そしてChapter 10だけが「開発プロセスそのもの」を扱う異質な章であり、このeラーニングの開発を題材にした締めくくりになっている。

## 自律開発の起動手順

### 初回セットアップ
```bash
brew install tmux   # tmuxのインストール（初回のみ）
```

### 毎回の起動手順（寝る前など）
```bash
# 1. tmuxセッションを作成
tmux new -s ai-learning

# 2. プロジェクトへ移動
cd ~/git/ai-learning

# 3. Claude起動
claude

# 4. 指示を出す
#    「launchして」

# 5. 動き出したのを確認してデタッチ（バックグラウンドに回す）
#    Ctrl+B → D
```

### 進捗確認・再開
```bash
tmux attach -t ai-learning   # セッションに戻る
```

> **tmux とは**: ターミナルを閉じてもセッションを維持できるターミナルマルチプレクサ。これがないと、PCのスリープ中にClaude Codeが止まってしまう。自律開発のインフラとして不可欠なツールだ。

## 実装ハイライト

### Rust/Axum バックエンドの追加

**何を作ったか**

`backend/` ディレクトリに Rust + Axum のサーバーサイドアプリケーションを新設した。認証（ユーザー登録・ログイン・JWT 発行）と進捗管理（レッスン完了状態の保存・取得）を担当する API サーバーだ。依存クレートは `axum 0.7`・`sqlx 0.8`（SQLite）・`jsonwebtoken 9`・`bcrypt 0.15` など。`backend/src/` の構成は `auth.rs`・`handlers/`・`models/`・`routes/`・`state.rs` に分かれ、責務が明確に分離されている。

**設計の意図**

それまで進捗管理はブラウザの `localStorage` に保存していた。この方式は手軽だが、端末をまたいだ学習継続ができない・セキュリティ上ユーザー固有データをクライアントに置く懸念がある・将来の集計・分析に耐えられない、という3つの問題を抱える。

サーバーサイドに移行することでこれらを一気に解決する。特に「どのレッスンを完了したか」という進捗データは、ユーザーのアカウントに紐づく本質的にサーバー側の情報であり、最初からサーバーで管理すべきだった。

Rust を選択した理由は、コンパイル時の型安全性が高く「動かしてみたらランタイムエラーが出た」というケースが減ること、Axum が Next.js App Router と設計哲学（非同期・型安全・ミドルウェア構成）が近く、フルスタック全体のコードを読む際に認知負荷が低いことが挙げられる。

**技術的なポイント**

SQLite + SQLx の組み合わせは、RDB の恩恵（スキーマ・マイグレーション・JOIN）を得ながらサーバーをシングルバイナリで運用できる。ステートレスな JWT 認証と組み合わせることで、セッション管理のインフラが不要になる。`backend/migrations/` でスキーマ変更を管理しているため、チームが増えても DB の状態が再現できる。

### 認証ガードの追加

**何を作ったか**

`src/middleware.ts` に Next.js Middleware を実装した。`/lessons` と `/dashboard` 配下のルートを保護対象として定義し、Cookie に JWT トークンが存在しない状態でアクセスした場合は `/login` へリダイレクトする。リダイレクト先 URL には `?from=元のパス` パラメーターを付与し、ログイン後に元のページへ戻れるようにした。

**設計の意図**

認証ガードを各ページコンポーネントに書くのではなく Middleware（リクエスト処理の前段）に集中させた理由が2つある。

1つ目は**DRY**（Don't Repeat Yourself）。ページが増えるたびに認証チェックを書かなくてよい。2つ目は**早期リダイレクト**。Middleware は Edge Runtime で動くため、コンポーネントのレンダリングやデータフェッチが始まる前にリダイレクトが完了する。認証されていないリクエストが DB クエリやサーバー処理を無駄に実行しない。

**技術的なポイント**

Next.js の `config.matcher` を `['/lessons/:path*', '/dashboard/:path*']` と指定することで、Middleware が必要なルートにだけ適用される。すべてのリクエストで Middleware が動くことによる余分な処理を回避している。Cookie から取得するトークンの存在チェックのみ（署名検証まではしない）のは、Edge Runtime の制約と応答速度のトレードオフを考慮した意図的な設計だ。

### フルスタック開発スキル群の追加

**何を作ったか**

フルスタック機能開発を担うスキル群を新設した。

| スキル | 役割 |
|---|---|
| `develop` | 機能開発のオーケストレーター。要件分析・API仕様決定・並列実装・検証・コミットを自律完結 |
| `frontend-developer` | Next.js フロントエンドの実装スペシャリスト |
| `api-developer` | Rust/Axum バックエンドの実装スペシャリスト |
| `design` | 機能の設計・仕様書作成 |
| `visual-review` | UIの視覚的なレビュー |
| `integration-test` | フロントとバックエンドの結合テスト |

`develop` スキルの核心は「スコープ判定」だ。UIのみの変更なら `frontend-developer` だけ起動し、フルスタックな新機能追加なら両者を並列起動する。つまり `develop` はオーケストレーターとして、変更の性質に応じて適切なサブエージェントを選択・組み合わせる。

**設計の意図**

`ship` スキルが「PRD のタスクを全部やり切るオーケストレーター」であるのに対し、`develop` スキルは「1機能を設計から完成まで持っていくオーケストレーター」だ。粒度が異なる2つのオーケストレーターが存在することで、「全機能を一気に進めたいとき（ship）」と「特定の機能を丁寧に作りたいとき（develop）」の両方に対応できる。

API仕様を `/tmp/api-spec.md` に書き出してから frontend-developer と api-developer に渡す手順も重要だ。両者が「同じ仕様書から出発する」ことで、並列実装していても型・エンドポイント・レスポンス形式の不整合が起きにくい。これが並列エージェントの品質を保つ「共通言語」の役割を果たす。

**技術的なポイント**

`develop` スキルのフローにある STEP 7「CHRONICLE」が今回の新設ステップだ。コミット完了後に必ず `chronicle` スキルを呼び出し、今回の実装を開発ジャーナルに記録する。「機能を作って終わり」ではなく「作ったことを記録して完了」というループを強制する仕組みだ。

### improve スキルの追加とオーケストレーター連携

**何を作ったか**

`improve` スキルを新設した。PRD のタスクがすべて完了した後に起動し、プロダクトを多角的に分析して改善アイデアを自律的に生成・実装する。SCAN（現状把握）→ ANALYZE（改善領域特定）→ IDEATE（アイデア生成）→ PRIORITIZE（優先度付け）→ IMPLEMENT（上位3件を実装）→ REPORT（結果報告）の6ステップで動く。

評価する8領域は UX/UI・パフォーマンス・アクセシビリティ・コンテンツ品質・学習体験・新機能・コード品質・SEO/メタデータだ。Impact × Effort マトリクスで優先度を決め、High Impact × Low Effort のアイデアを即実装する。

`launch` スキルの IMPROVE フェーズに組み込み、全サブエージェント（ship・content・chronicle）完了 + PRD の全タスクにチェックがついた場合に自動起動するようにした。「やるべきことをやり切った後、次の改善候補を自分で見つけて実装する」というループが実現した。

**設計の意図**

自律開発における最大の課題の一つは「タスクが尽きたときに止まってしまうこと」だ。`improve` スキルはこの問題を解決する。PRD という有限のタスクリストが完了した後も、プロダクト分析からアイデアを生成し続けることで、エージェントが自律的に価値を生み出すサイクルを持続させる。

再実行性も設計した。「improve して」と再度依頼すると、前回レポートの「残りのアイデアリスト」から続きを実装する。毎回ゼロからアイデアを出し直すのではなく、前回の判断を引き継いで続きから進む。

### chronicle 自動記録ステップの追加

**何を作ったか**

`ship`・`develop`・`launch` の各スキルに、コミット後に `chronicle` スキルを呼び出す自動記録ステップを追加した。従来は「記録して」と明示的に依頼しないと開発ジャーナルが更新されなかったが、この変更により機能を作れば必ず記録が残るようになった。

**設計の意図**

記録は「後でやろう」と思うと確実に漏れる。これは人間でも AI エージェントでも同じだ。ましてやエージェントは各スキル実行の文脈が終わったら「今何をやったか」の記憶が薄れていく。コミット直後という「実装が最も鮮明なタイミング」に強制的に記録させる仕組みが不可欠だった。

ship・develop という開発実行スキルと chronicle という記録スキルを分離した理由は、関心の分離だ。ship や develop は「何を作るか・どう作るか」に集中し、chronicle は「何を作ったか・なぜそうしたか」に集中する。しかし最終的には両者は必ずペアで動くべきものだ。今回の自動連携はその設計意図を実装で表現したものだ。

## 意思決定メモ

**なぜ進捗管理を localStorage からサーバーサイドに移行したか**

当初の localStorage 方式は「スタート地点」として妥当だった。フロントエンドのみで完結するシンプルさが初期実装のスピードを上げる。しかし学習進捗という「ユーザーが最も大切にするデータ」をブラウザのローカルストレージに置いたままスケールするのは無理がある。ブラウザのキャッシュクリアやデバイス変更で消えるデータを「学習の記録」とは呼べない。Rust/Axum バックエンドの追加と同時に移行することで、フロントエンドとバックエンドの型整合を最初から取れるメリットもあった。

**なぜ Next.js Middleware で認証ガードを実装したか**

ページコンポーネント内での `useEffect` によるクライアントサイドリダイレクトは、一瞬コンテンツが見えてから飛ばされる「フラッシュ」が起きる。Server Component 内での認証チェックはページごとに書く必要がある。Middleware は Edge Runtime でリクエストの最前線で動くため、フラッシュが起きず、かつ認証ロジックを一箇所に集約できる。この方式が現状のベストプラクティスだ。

## ハーネスエンジニアリングの学び

**スキル設計の「粒度」と「連携」のバランス**

今回のスキル追加で、スキル体系が大きく深化した。`launch` → `ship/content/chronicle` という2層から、`launch` → `ship(→develop→frontend-developer/api-developer)` という3層構造になった。粒度が細かくなるほど各スキルの責務が明確になるが、オーケストレーションの複雑さも増す。

学んだことは「スキルは依頼の粒度に合わせて設計する」ということだ。「全部やって」は `launch`、「この機能を作って」は `develop`、「このコンポーネントを作って」は `frontend-developer`。依頼の抽象度に対応した受け口を用意することで、どんな粒度の依頼でも適切なスキルにルーティングできる。

**「chronicle を自動化する」という判断の意義**

chronicle の自動化は小さな変更に見えるが、開発文化の変革を意味する。「記録は大事だが後回しになりがち」という普遍的な問題を、「記録をスキップできない仕組み」で解決した。

これはソフトウェアエンジニアリングの原則「Make the right thing easy, the wrong thing hard」そのものだ。chronicle を呼ぶのが「デフォルト」になり、呼ばないことが「例外」になる。ハーネス（馬具）が馬の力を正しい方向に導くように、スキル設計がエージェントの行動を望ましい方向に誘導する。

**improve スキルが示す「無限に改善し続けるエージェント」の可能性**

PRD という有限のゴールを超えて動き続けるエージェントの設計は、これまでの「タスクリスト実行型」AI との本質的な違いを生む。PRD はスタート地点の合意に過ぎず、その後のプロダクト成長は継続的な改善の積み重ねだ。`improve` スキルはその改善サイクルを自律化する最初の試みだ。Impact × Effort マトリクスによる優先度付けは、人間のプロダクトマネージャーが行う判断をスキルに埋め込んだものだ。

ループの終了条件は2つだけに限定した：
1. 新しいアイデアを生成しても High/Medium Impact のアイテムがゼロだった場合
2. 連続して3件以上のスキップが発生した場合（詰まっているサイン）

上記のいずれかに該当するまで、STEP 1 → STEP 4 → STEP 5 → STEP 6 を繰り返し続ける。

**設計の意図**

バックログ管理（前のコミット）で「前回の続きから再開」という問題は解決した。しかしまだ「バックログを全部消化したら止まる」という天井があった。これを取り除くのが今回の変更だ。

`improve` スキルのあるべき姿は「開発タスクがなくなったときに動き続ける永続エンジン」だ。バックログが空になったからといって、プロダクトに改善の余地がなくなったわけではない。再びスキャンして分析すれば、前回とは違う観点の改善アイデアが見つかるはずだ。ループを止める条件を「High/Medium Impact がゼロ」という価値ベースの判断にしたことで、「改善する価値がある限り動き続ける」エージェントが実現した。

**技術的なポイント**

「連続3件以上のスキップで停止」という安全弁が重要だ。ループを無限に回すと、スキップが続いてもエージェントが止まれず、どこにも進まない状態で延々と実行し続けるリスクがある。スキップカウンターを持つことで「詰まりを検知して停止する」フェイルセーフを組み込んだ。自律実行系のスキルには必ず「いつ止まるか」の明示的な条件が必要だ。これはソフトウェアの無限ループ防止と同じ原理だ。

## 意思決定メモ

**なぜ「上位3件を実装して終了」から「全件実装しきるまで継続」に変えたか**

前の improve スキルは「1セッションで3件」という暗黙の制限があった。これは当初の設計が「人間が確認しながら進める前提」だったためだ。しかし自律実行を前提にするなら、3件で止まる理由はない。バックログに10件積まれているなら10件全部やるべきだ。「途中で止まる」という行動は自律エージェントとして不完全だ。

**バックログを `docs/` に置く理由**

`.claude/` に置かなかった理由は、バックログは「現在の実装状態の一部」であり、コードと同じリポジトリで管理されるべきだからだ。エージェントが何を実装したか・何が残っているかは、開発ジャーナル（`docs/journal/`）と同様にプロジェクトの歴史として記録されるべき情報だ。`.claude/` は「エージェントへの指示」を置く場所であり、「プロジェクトの状態」を置く場所は `docs/` が適切だ。

## ハーネスエンジニアリングの学び

**「終わり方」の設計が自律エージェントの品質を決める**

今回の2コミットは、どちらも「スキルがどこで止まるか」という問いへの答えだ。自律エージェントは「どう動くか」だけでなく「いつ止まるか」「次にどこから再開するか」が設計されていないと、1回限りのバッチ処理に過ぎない。バックログによる再開可能性とループによる継続性を組み合わせることで、improve スキルは真の意味で「永続エンジン」になった。

**状態の外部化がエージェントの記憶を補う**

コンテキストウィンドウは有限だ。セッションをまたいで記憶を持つことはできない。`docs/improve-backlog.md` はその制約を補う「外部記憶」として機能する。何を実装したか・何が残っているか・前回はなぜスキップしたかが、ファイルに記録されている限り、エージェントは前回の自分の判断を引き継げる。

この設計パターン（状態をファイルに外部化する）は improve スキル固有の話ではない。長時間実行・マルチセッションにまたがるあらゆる自律エージェントに適用できる普遍的な原則だ。
